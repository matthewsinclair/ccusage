## Symptom

Claude Usage lists engineering.01@geodica.com twice.

## Cause (2026-11-03; metadata and scratch configs only, no secret read)

- Claude Usage lists every `Claude Code*` Keychain item: `security dump-keychain | grep -o '"svce"<blob>="Claude Code[^"]*"'`.
- Claude Code names a login's item after a directory. The name is `Claude Code-credentials-` plus the first 8 hex digits of the SHA-256 of `CLAUDE_SECURESTORAGE_CONFIG_DIR` when that is set (taken as given, NFC-normalised, not resolved), else of the config directory. The account is `$USER`.
- The five ccusage profiles hold five logins, one per account. The main config, `/Users/matts/.config/claude`, where the sessions run, holds a sixth of its own: `ca646b28`, currently engineering.01. Whichever account the main config is signed into duplicates one of the five.
- ccusage never creates Keychain items. Its `login` creates a profile's login through `claude auth login`, and that is the login to keep.

## Design (hv, 2026-11-03: switch accounts with ccusage, never `/login`; restarting a session to switch is acceptable; `ccusage use` may write `oauthAccount` into the shared `.claude.json`)

One login per account, in its ccusage profile. Sessions keep the shared config and borrow the active profile's login.

- Sessions run with `CLAUDE_CONFIG_DIR=~/.config/claude` and `CLAUDE_SECURESTORAGE_CONFIG_DIR` set to the active profile's directory. Claude Code then reads, renews and locks that profile's item. Its refresh lock (`.oauth_refresh.lock`, plus the legacy `<dir>.lock`) and its write lock (`.storage-write.lock`) live in the credential directory, which is where ccusage already takes them.
- Claude Code shows the account recorded as `oauthAccount` in the config's `.claude.json`, not the credential's account, and it never replaces that record with another account's profile. Verified on scratch configs: an engineering02 credential under an engineering.01 record reports engineering.01, and with no record it reports no email. So `ccusage use NAME` also writes NAME's `oauthAccount` into the shared config's `.claude.json`. It copies the record from NAME's own profile `.claude.json`, where Claude Code wrote it at `ccusage login`, takes Claude Code's `.claude.json` lock, and changes no other key.
- Running sessions keep their login until they are restarted.

## Fix outline

- Config: a top-level `claude_config_dir` (eg `"~/.config/claude"`) turns on shared mode. With it unset, ccusage behaves exactly as now.
- `ccusage dir [NAME]` prints the active or named profile's directory exactly as ccusage hashes it, for a launcher to export as `CLAUDE_SECURESTORAGE_CONFIG_DIR`. With no active profile it prints nothing and exits nonzero, because an empty value means `~/.claude` to Claude Code.
- `ccusage use NAME` in shared mode selects NAME, writes its `oauthAccount` into the shared config, and says that new sessions use NAME and running ones switch when restarted.
- `ccusage run [NAME]` in shared mode keeps `CLAUDE_CONFIG_DIR` at the shared config and sets `CLAUDE_SECURESTORAGE_CONFIG_DIR`. `run NAME` for a profile that is not active switches first, as `use` does, so the record always matches the login.
- `ccusage login NAME` is unchanged: it signs in within the profile's own directory.
- `doctor` warns when the shared config still holds its own login while shared mode is on (the login to retire), when the shared `oauthAccount` does not match the active profile's, when `CLAUDE_SECURESTORAGE_CONFIG_DIR` in the environment names no profile, and when a profile directory has no config entry (`engineering03`).
- On macOS, `ccusage use` in shared mode also sets launchd's `CLAUDE_SECURESTORAGE_CONFIG_DIR` with `launchctl setenv`, as Molt already does for `CLAUDE_CONFIG_DIR`, so Claude Code started from a GUI app follows the active account too. `doctor` warns when launchd's value names no profile or not the active one.
- README documents shared mode and the one-line launcher export.

## From 0.1.9: one live login (ST0003)

From 0.1.9, shared mode keeps one live login, which a switch moves (ST0003). hv took ST0003's route on 2026-11-13, after its WP01 trial passed. The shared config's own login, `ca646b28`, becomes the one login every session reads, and `ccusage use NAME` moves NAME's login into it and the previous account's back to its profile. Sessions then need nothing from their launcher but `CLAUDE_CONFIG_DIR`, which removes the stale-shell fault above. So this issue no longer waits on a launcher fix ("Left to close" above), and step 4, retiring `ca646b28`, must not run, because that login is now the live one.

The decision record is "Shared mode keeps one live login, which a switch moves" in `intent/llm/ARCHITECTURE.md`, which cc lands with ST0003/WP05. This issue closes at ST0003/WP06's rollout on rhadamanth, with Acceptance 1 and 5 read against ST0003's layout.
