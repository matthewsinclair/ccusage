No login was read, renewed or moved.

## Symptom

On rhadamanth, ccusage 0.1.9 (brew, 2762bbf961ea), 2026-11-16:

- `ccusage usage --all --verbose` shows engineering01 as "stored Claude login does not match this profile's email; authenticate the intended account in its dedicated directory". On 2026-11-13 the same line stood against hello. hv has repaired it by `ccusage login NAME` three times since (engineering04 and hello on 2026-11-15, engineering01 on 2026-11-16 at 10:32Z), and it comes back.
- `ccusage doctor` exits 1: "hello has two logins, the shared config's and another in its own store, so a switch away from hello is refused; run ccusage login hello, which leaves it one login". The same run says "OK engineering01's login is in its own store".
- `ccusage which` names engineering02 as next and `ccusage predict` projects every account filling to the cap, while engineering00, engineering02 and engineering04 stand at 0% and hello alone climbs: 3% at 10:30Z, 41% at 17:12Z, about 5.7% of a weekly allowance an hour. predict gives the burn rate as 1.3% an hour.

## Cause

One cause carries all three: Claude sessions are still started with `CLAUDE_SECURESTORAGE_CONFIG_DIR` naming a profile's own store, after hello was seated in the shared config on 2026-11-15 at 19:19Z (`seat.json`), and ccusage neither stops that nor says what it does.

1. **Where the pin comes from.** Molt's `env.sh` sets or unsets the variable once, when a shell starts, from `ccusage dir`. A fresh shell has it unset today. But 85 of the zsh shells alive on rhadamanth started on 2026-11-12, when `ccusage dir` printed hello's profile directory, and each still exports that. The fleet restarted on 2026-11-16 between 16:06Z and 17:00Z from those shells: of 29 sessions, 24 run with hello's profile directory, 1 with engineering01's, and 4 with none.
2. **The loop doctor's remedy makes.** `ccusage login hello` on the seated account puts the fresh login in the shared store and leaves hello's own store empty (`switch::reseat`). The sessions pinned to that store then have no login. A `/login` typed in any one of them writes a login into hello's own store, which Claude Code does with no check of whose it is. doctor then fails with two logins again, `ccusage use` away from hello is refused (`Refusal::Occupied`), and its remedy is `ccusage login hello` again.
3. **How a store comes to hold another account's login.** engineering01 stood at 100% from 2026-11-15 06:36Z. Usage read it, verified, at 12:04:10Z on 2026-11-16. At 12:41:47Z its own store's Keychain item was rewritten, in the same second the shared `.claude.json` recorded hello's account as fetched: a `/login` as hello inside the session pinned to engineering01's store. Usage refuses that login, as it should. doctor's `where_logins_are` asks only whether a store holds a login, never whose, so it says OK.
4. **predict's rate drops the account that did most of the burning.** `predict::project` counts the samples of one plan's accounts, and an account whose report failed has no plan, so all 58 of engineering01's weekly samples leave the rate: 64 of the 165 points that rose in 77 hours. With them the history gives 2.1% an hour from 84 samples; without, the 1.3% from 26 that predict prints. Nothing in its output says an account's history was left out.
5. **which, predict and the TUI assume the fleet follows the rule.** With 25 of 29 sessions pinned, no switch moves them, and a switch away from hello is refused anyway. Only doctor says a session is pinned.

One more thing the history shows, which ccusage did not cause and does not flag: a weekly percent fell inside one window twice. engineering04 read 38% at 11:20:53Z and 9% at 14:23:12Z on 2026-11-15, both on the window resetting 2026-11-16T12:00Z. hello read 80% at 19:19:20Z on 2026-11-15 and 6% at 06:56:55Z on 2026-11-16, both on the window resetting 2026-11-16T10:00Z. Each figure is what the usage endpoint returned to a token the profile endpoint named as that account. `history::record` keeps a fall, and `predict::rate` counts it as no rise. Why the endpoint's figure fell is not something this machine shows.

## Severity

High. hv cannot move the fleet off the active account: the switch is refused, the tool's own remedy puts the fault back, and three accounts' weekly allowances go unused while the active one runs out. No login is lost and nothing is exposed.

## Live repair

hv's hands, vc checking after each step from metadata. It is ST0003/WP06's rollout, from where rhadamanth now stands:

1. Every shell that starts Claude loses the pin: a fresh shell, or `unset CLAUDE_SECURESTORAGE_CONFIG_DIR` in a shell that stays.
2. Every pinned session restarts from such a shell, so that no `claude` process carries the variable.
3. `ccusage login hello`, then `ccusage login engineering01`, then `ccusage doctor` with no FAIL and no pinned session.
4. `ccusage which`, then the switch it names, which the running sessions follow (AC-06.1, AC-06.2).

## Fix outline

Code, for Ccusage's next release, tested in a throwaway HOME and XDG tree as the standing rule has it:

1. doctor says whose login each profile's own store holds, checked as `usage::whose` checks the shared one and renewing nothing. Another account's is a FAIL, and it names each session pinned to that store.
2. doctor's finding for two logins, and usage's refusal of a login that is not the profile's, give the remedy in the order that works: while a session is pinned to that store, restart it from a shell without the variable first, and only then `ccusage login NAME`. Each names the pinned sessions, or says there is none.
3. `ccusage login NAME`, `ccusage use NAME`, `use --none` and `which --use` refuse, before anything moves, a move that would empty a store a running session is pinned to, and name the sessions. Whether a flag overrides the refusal, and its spelling, is cc's proposal to vc.
4. A verb that reports (doctor, which, predict, usage) says so when the shell it runs in exports the variable while a profile is seated, with the one command that clears it.
5. predict's rate keeps the samples of an account whose fetch fails now, on the plan its last good fetch recorded, and its output names any account whose samples it leaves out, with how many.
6. which, predict and the TUI say how many running sessions are pinned and so do not follow the account they name. Text only: a change to a `--json` shape waits for ic.
7. predict says so when a window's newest sample is below an earlier one in the same window, as the endpoint reported it.

Outside Ccusage, for hv to place: a shell that outlives a switch keeps its pin, since Molt's `env.sh` runs at shell start alone. Whatever starts a fleet session could work the variable out at each launch, as `env.sh` does for a shell.

## Acceptance

- With a profile's own store holding another account's login, `ccusage doctor` fails on that profile and names each running session pinned to that store; with the profile's own login there, it says OK as it does now.
- With the seated profile holding a second login in its own store and a session pinned to that store, doctor's remedy puts the restart of the pinned sessions before `ccusage login NAME`; with no session pinned, the remedy is `ccusage login NAME` alone.
- `ccusage login NAME` and a switch that would empty a store a running session is pinned to are refused before any login moves, with the sessions named.
- `ccusage predict` gives the same rate whether or not an account's fetch fails now, when that account's last good fetch was on the counted plan, and names any account whose samples it leaves out.
- which, predict and the TUI each say how many running sessions are pinned, and say nothing of it when none is.
- On rhadamanth after the live repair: `ccusage doctor` exits 0 with no pinned session, every account reads its own usage, and a switch moves the running sessions.
