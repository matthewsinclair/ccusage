## Fix outline

devbin#0326's three parts, as devbin-vc agreed them on 2026-11-06 (from devbin-cc's message to vc; the key names are what devbin builds next). None of it works until the devbin release carrying 0326 is vendored with `bin/devbin upgrade`, and nothing that depends on it is released before then.

1. Ccusage declares an `install:` block in `bin/.devbin/config.yaml`: `prefix`, the opt prefix (eg `~/opt/ccusage`; it has no default); `links`, here `ccusage: target/release/ccusage`; and, only where needed, `files`, each a label with `path`, `from` and `platforms`. `formula.bin` goes, because the link set replaces it. The manifest is `<root>/.ccusage-install`.
2. `bin/devbin build` exports `DEVBIN_VERSION_LINE` into Ccusage's declared build (`cargo build --release --locked`). For `--version`, the binary prints the manifest's `# line:` when `<its own directory>/../.ccusage-install` holds one naming ccusage; else `option_env!("DEVBIN_VERSION_LINE")`; else `ccusage <version> (unknown, unknown)`. The contract spells those few lines of Rust once. `bin/devbin doctor` in Ccusage's checkout runs `ccusage --version` and fails when its line differs from the core's. ccusage gains no `version` verb.
3. The formula's install body is `@@INSTALL@@` on both branches, followed by the template's own signature check. Each archive is rooted at the install root with the binary at `bin/ccusage`, so it lands at `libexec/bin/ccusage` in every keg, and `verify_macos_signature` reads `libexec/"bin/ccusage"`. The Linux branch, a source checkout holding `bin/devbin`, runs `bin/devbin install --prefix libexec --managed-by brew` and keeps `depends_on "rust" => :build`. The caveats name `bin/devbin use`, run in the checkout, for a maintainer with a dev or opt tree (T8).

The archive's move touches the release build's staging (`.github/workflows/build.yml:73`), the signer's exact file list and its tests (`bin/.devbin/cmd/macos:16-17` and `:38`), and the formula template. The archive's other three files (LICENSE, README.md and ccusage-logo.svg) would then land in libexec too. Declaring them under `install.files` or taking them out of the archive is the wiring's choice, and the Linux branch's `pkgshare.install` of the logo follows it.
