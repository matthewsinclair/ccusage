## Symptom

The first ccusage run of the day works. Moments later macOS shows `security wants to access key "Claude Code-credentials-<hash>" in your keychain. To allow this, enter the "login" keychain password.`, once per registered profile. "Always Allow" does not stop it coming back the next day.

## Evidence (2026-11-03; metadata and ACLs only, no secret read)

- The prompting program is `/usr/bin/security`, not ccusage. Claude Code reads its items with `security find-generic-password -a <user> -w -s <service>` and writes them through `security -i`, with `add-generic-password -U -a ... -s ... -X <hex>` on stdin. Claude Usage (`com.helpfully.ClaudeUsage`) lists items with `security dump-keychain` and reads each with `security find-generic-password`.
- ccusage reads and writes the same items as itself, through Security.framework: `read_keychain` (`src/auth.rs:133`) and `save_keychain` (`src/auth.rs:118`, `SecKeychainItem::set_password`). It never calls `/usr/bin/security`.
- ccusage's renewal wrote the five profile items in place between 06:56:17Z and 06:56:22Z (mdat). Their creation dates (2026-10-27, 2026-10-31) are unchanged, so nothing is re-created.
- Items ccusage has never written (`ca646b28` for `~/.config/claude`, and the orphan `9d96588d`) have partition list `apple-tool:` and trust only `/usr/bin/security`.
- Items ccusage has written (`7a2ec3d6` engineering04, `e4383f82` hello) have partition list `teamid:76BQL8L47U, apple-tool:` and trusted apps `ccusage 0.1.5`, `ccusage 0.1.3` (a stale path) and `/usr/bin/security`, in that order. `apple-tool:` and `/usr/bin/security` come after ccusage's entries: today's "Always Allow" added them back after ccusage's write had removed them.

## Cause

ccusage's in-place write resets the item's partition list to ccusage's own partition (`teamid:76BQL8L47U`) and drops `apple-tool:`. From then on, every `/usr/bin/security` access (Claude Code, Claude Usage) hits the partition-mismatch password prompt. "Always Allow" appends `apple-tool:` again, and the next renewal strips it. The stable signing identity in v0.1.4 dealt with prompts for ccusage itself, so it could not help with this one.

Proven on 2026-11-03 by dc's red test `renewal_write_keeps_claude_items_readable_by_security` at `d6408f1`, and reproduced by vc on an exact export: after ccusage's in-process write, the item's partition list is the writer's own `cdhash:` alone, with `apple-tool:` gone. dc's fix landed as `812264d`. On 2026-11-03 vc validated it on an exact export, against every Acceptance item that can be checked before release. After the renewal write, the item's partition list is `apple-tool:` alone and its decrypt ACL keeps `/usr/bin/security`. No credential bytes reach a process argument. `security -i` reads a line of up to 4097 bytes, newline included, whole, and still runs the first fragment of a longer one, so the 4032-byte limit is what keeps a renewal from writing a truncated document. CI on both macOS targets and the post-release check remain.

## Fix outline

- Reach Claude's credentials the way Claude Code does. Read with `/usr/bin/security find-generic-password -a <user> -w -s <service>`. Write with `/usr/bin/security -i`, sending the `add-generic-password -U` command on stdin.
- The secret never goes in a process argument. If the document is larger than `security -i` accepts on stdin, refuse with a clear error rather than fall back to argv the way Claude Code does.
- Keep the update-only rule. `-U` creates a missing item, so check that exactly one item exists before writing. Keep the refresh and write locks and the no-plaintext-fallback rule.
- ccusage then needs no Keychain trust of its own and stops prompting for itself. Rewrite README's Keychain paragraphs to match.

## Acceptance

- A macOS test on a disposable keychain creates an item with `/usr/bin/security`, as Claude Code does, runs ccusage's renewal write, and asserts that the item still has `apple-tool:` in its partition list and `/usr/bin/security` in its decrypt ACL. It fails on the current code (red) and passes after the fix (green). User interaction is disabled throughout, so the test fails rather than prompts.
- The same test asserts that a write to a missing item fails and creates nothing.
- No code path passes credential bytes in a process argument.
- CI runs the test on both macOS targets. It replaces `native_keychain_updates_existing_item_without_plaintext_fallback`, which creates its item in-process and so cannot see this failure.
- After release, a renewal on hv's machine raises no prompt and leaves `apple-tool:` on the item (checked with `security dump-keychain -a`, metadata only).
